# AGENTS.md

## Область применения

Этот репозиторий — библиотека на Rust для работы с ISS API Московской биржи. Описание ISS API доступно по ссылке: <https://iss.moex.com/iss/reference/>

Оптимизировать решения по критериям корректности, строгой типизации, компактного дизайна и эффективности исполнения.

## Основные правила

- Предпочитать идиоматичный Rust(edition 2024) и современные конструкции языка и стандартной экосистемы вместо устаревших паттернов.
- Держать кодовую базу компактной: переиспользовать код, предпочитать обобщения и небольшие абстракции дублированию.
- Следовать принципу "parse, don't validate": один раз парсить внешний ввод в более строгие типы, которые кодируют инварианты.
- Предпочитать type-driven design вместо API на сырых строках и разрозненных проверок по коду.
- Избегать heap-аллокаций на горячих путях, если нет ясной и задокументированной причины.
- Где это практически уместно, предпочитать заимствование, zero-copy парсинг, срезы и представления, дружественные к стеку.
- Избегать лишних `clone`, промежуточных `String`/`Vec` и повторного парсинга.
- Prefer bounds-check elimination patterns: iterators, slices/subslices, chunking, provable index ranges, loo   p-invariant prechecks, etc.
- Не использовать `unsafe`, кроме случаев реальной необходимости; он должен быть изолирован, обоснован и покрыт тестами.
- Пиши doc-strings и комментарии на русском. Только там где это нужно и полезно.
- Сообщения в консоль: ошибки, ворнинги итд должны быть на английском.
- Используй файловую структуру модулей Rust 2018+: foo.rs и foo/bar.rs, без foo/mod.rs.
- Библиотека находится в разработке, поэтому сохранять обратную совмесимость не обязательно и релиз-ноды писать тоже.
- Для обычного текста не делай "ручной" перенос на новую строку.

## Дизайн API

- Публичный API должен быть небольшим, явным и предсказуемым.
- Моделировать предметную область через `enum`, newtype и специализированные `struct`, а не через сырые строки и слабо типизированные словари.
- Централизовать пути эндпоинтов, имена query-параметров и особенности wire-format; не дублировать их по кодовой базе.
- Держать DTO wire-format внутренними, если можно предоставить более строгие публичные доменные типы.
- Вводить абстракции только тогда, когда они действительно устраняют дублирование или выражают инвариант.
- Имена переменных и названия методов должны по возможности совпадать с используемыми в MOEX ISS API.
- Приоритет нужно отдавать fluent interface(method chaining).

## Предпочтения по реализации

- Предпочитать гарантии времени компиляции проверкам во время исполнения.
- Предпочитать полные и локализованные преобразования (`TryFrom`, smart constructors, функции-парсеры) на границах системы.
- Держать модули сфокусированными и цельными.
- Когда производительность и простота конфликтуют вне горячих путей, предпочитать более простое решение; на горячих путях — более быстрое.
- Изменения, влияющие на парсинг, аллокации или обработку запросов/ответов, подтверждать бенчмарками.

## Ошибки

- Использовать структурированные типы ошибок.
- Ошибку отдавать рано на некорректных данных от внешнего API.
- Не падать с паникой.
- Сохранять контекст источника и включать достаточно деталей, чтобы можно было определить проблемный эндпоинт или поле.
- Не делать молчаливых "best effort" преобразований некорректных данных.

## Тестирование и проверка

- Добавлять unit-тесты для парсинга, инвариантов и граничных случаев.
- Добавлять regression-тесты для каждого исправленного бага.
- Добавлять integration-тесты для типичных ответов ISS.
- После изменений запускать:
  - `cargo fmt --all`
  - `cargo clippy --all-targets --all-features -- -D warnings`
  - `cargo test --all-features`
